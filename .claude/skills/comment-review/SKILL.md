# コメント精査

コードのコメントを読み手の視点で評価し、改善が必要なものを理由付きで指摘する。

## 基本の考え方

コードを読めばすぐにわかることは書かない。本当に必要な内容だけを記述する。

コメントを書くのは、そのコードを読んだだけでは実装内容を理解できないと思われる場合に限る。「実装内容は分かるが、なぜそうしたのかが分からない」はコメントの出番ではなく、ADR・コミットメッセージ・PR などの判断記録や履歴が担う。コメントはコードと一緒に古くなるため、コードから読み取れる情報や、記録として別の場所に残すべき情報を抱えるほど、嘘になるリスクだけが増える。

## 手順

1. **対象を決める。** ユーザーが指定したファイルやディレクトリを対象にする。指定がなければ、`git diff` があればその差分、なければプロジェクト内のソースコードを対象にする。生成物、vendor、lock ファイル、ライセンスヘッダーは除外する。
2. **コメントとその周辺コードを読む。** コメント単体ではなく、対応するコードと一緒に読む。コメントとコードが食い違っていないか確認するため。
3. **各コメントを下の観点で評価する。** 問題がないコメントは報告しない。ノイズになるため。
4. **指摘をまとめて報告する。**

## 指摘する観点

### A. 意味のないコメント(消してよい)

- **コードの言い換え** `i += 1  # i を 1 増やす`、`# ユーザーを取得する` の直後に `get_user()` がある、など。
- **名前の繰り返し** 関数名や引数名をそのまま文章にしただけのdocstring。
- **特定の時点に依存するコメント** 仕様変更への追従など「その時点」でしか意味を持たないコメント。コード中のコメントではなく、コミットメッセージまたはPRに残すべき。
- **「なぜそうしたか」を説明するコメント** 実装の理由、設計判断、経緯。ADR、コミットメッセージ、PR に残すべき。コードを読んで実装内容が理解できるなら、理由が分からなくてもコードの問題ではなく、判断記録や履歴を見に行く話。
- **コメントアウトされたコード** 履歴はVCSにある。
- **変更履歴・作者名・日付** `# 2023/4 追加`、`# 田中修正`。VCSの役割。
- **修正済みの TODO/FIXME** 対応が終わっているのに残っているもの。

### B. 読み手を考慮できていないコメント(直すべき)

- **コードと食い違っている。** 最優先で指摘する。誤解を招くため、無いより悪い。
- **曖昧・指示語だらけ。** 「ここ」「これ」「例の件」「前述の」など、文脈がないと分からない表現。
- **内輪の文脈に依存している。** 過去の会話、社内用語、略語を説明なしに使っている。
- **位置が悪い。** 説明対象から離れている、関係ないコードの上にある。
- **コメントで補うより、コードで解決すべき。** 変数名・関数名を変える、関数に切り出す、定数に名前を付けることで、コメントが不要になるもの。
- **呼び出され方や呼び出される場所を書いている。** コードを読めばわかる。ほかの場所で利用するときにいちいち追記する必要があるので無駄。
- **クラスの責務や関心事からかけ離れた内容をコメントする** コードが守っている境界を破ってしまう。

### C. 残すべき・良いコメント(指摘しない)

次のようなコメントは価値があるので、消す方向の指摘をしない。

- 非自明な制約、前提条件、副作用、スレッド安全性
- ツール用ディレクティブ(`# noqa`、`// eslint-disable`、`# type: ignore` など)。理由が書かれていない場合のみ、理由の追記を提案する。

言語の慣習にも配慮する。公開 API の docstring を求める言語・プロジェクトでは、名前の繰り返しでも規約上必要な場合がある。その場合は「消す」ではなく「情報を足す」提案にする。

## 報告の形式

指摘は重要度順に並べる(コードとの食い違い → 読み手に誤解を与えるもの → 不要なコメント → 軽微な改善)。1件ごとに次を書く。

```
### <ファイルパス>:<行番号>
コメント: `<該当コメントの原文>`
分類: <意味がない / 食い違い / 理由・経緯の記述 / 曖昧 など>
理由: <読み手にとって何が問題か。1〜2文>
提案: <削除 / 書き換え案 / コード側の改善案>
```

書き換えを提案するときは、実際の書き換え文を示す。「もっと分かりやすく」のような抽象的な提案では使えないため。理由・経緯を書いたコメントの削除を提案するときは、内容を ADR・コミットメッセージ・PR のどれに移すのがよいかを添える。

最後に、短いまとめを付ける。

- 精査したコメント数と、指摘した件数
- 傾向(例: 「関数名の言い換え docstring が多い」)
- 良いコメントの例を1〜2件(基準の共有になるため)

指摘が1件もなければ、その旨を一言で伝える。無理に探さない。

## 注意

- ユーザーが「直して」と言わない限りファイルは編集しない。指摘と提案までが役割。
- コメントの言語(日本語・英語)は、プロジェクトの既存の流儀に合わせる。混在していること自体は、読み手に支障がなければ指摘しない。
- 好みの問題と、読み手に実害がある問題を区別する。実害がないものは「軽微」として分け、件数が多いときは省略してもよい。
