# 要件定義書: Automated Tech Info Digest System

最終更新: 2026-11-01

## 1. 目的

AI が最新の技術情報を毎日自動で収集・選定・要約し、その結果を Gamma でスライド化して Google Drive に保存する。完成したら Discord で通知する。

- 利用者は本人1名のみ。自分のインプット用であり、発表用途は想定しない。
- まずは**最高品質の出力を確認する**ことを優先する。Claude・Gamma への指示には費用を考慮した制約を入れない。費用が問題になった時点で改めて検討する。

## 2. スコープ

| 項目 | 内容 |
|---|---|
| 実行頻度 | 毎日1回、7:00 JST |
| 対象期間 | 前回実行以降に公開された記事 |
| 関心領域 | AI/LLM、Web フロントエンド、バックエンド/クラウド、インフラ/DevOps、アーキテクチャ、形式手法（設定で変更可能） |
| 言語 | 情報源は英語・日本語、出力は日本語 |
| AI による処理の深さ | 記事ごとの要約まで（記事横断の分析やパーソナライズは行わない） |
| 1日の掲載本数 | 10本（設定で変更可能） |

## 3. 情報源

公式 API または公式 RSS/Atom のみを使用し、非公開の内部 API は使用しない。情報源の一覧は `config/sources.yaml` で管理する。

| 情報源 | 取得方法 | 人気度シグナル | 備考 |
|---|---|---|---|
| 技術ブログ等の RSS | 各フィード | なし | 初期リストは実装開始時に作成し、本人が確認する |
| Hacker News | Algolia HN Search API（前回実行以降・100 points 超） | points、コメント数 | `numericFilters` は URL エンコードが必要 |
| GitHub Trending | `github.com/trending` の HTML を解析 | 当日のスター数 | 解析に失敗した日はスキップする |
| はてなブックマーク | `https://b.hatena.ne.jp/hotentry/it.rss` | ブックマーク数 | robots.txt の `Crawl-delay: 5` に従う |
| Zenn | トレンド RSS（`/feed`）、トピック別 RSS（`/topics/{topic}/feed`） | なし | |
| Qiita | API v2（アクセストークン付き） | いいね数、ストック数 | |
| TechFeed | 対象外 | | 利用規約で自動取得が禁止されている可能性があるため |

## 4. システム構成

処理を4つの工程に分ける。各工程は前の工程の出力**だけ**を入力とし、工程間は JSON で受け渡す。JSON のスキーマは `zod` で定義する。

```
① 収集・選定    ──▶ selection.json
② 要約         ──▶ digest.json
③ スライド生成  ──▶ PDF ＋ Gamma URL
④ 配信         ──▶ Google Drive 保存 ＋ Discord 通知
```

- 要約（②）はスライド生成を知らず、スライド生成（③）は要約の作り方を知らない。
- 中間ファイルは Drive に保存し、途中の工程から再実行できるようにする（例: 要約はそのままでスライドだけ作り直す）。
- ①は差し替えられる構造にする（将来、手動でリクエストした内容を入力にできるようにするため）。

### 4.1 ① 収集・選定

1. **収集**: 各情報源から前回実行以降の記事を取得する。
2. **重複統合**: URL を正規化し、情報源をまたいで同じ記事を1件にまとめる。人気度シグナルはすべて保持する。
3. **既出除外**: 直近30日以内に掲載した URL を除外する。
4. **関連度判定**: Claude **Sonnet 5.5** が、タイトルと RSS 概要を関心領域の説明と照らし合わせ、各候補に以下を付与する。
   - 関連度（0〜100）
   - 分野（`config/interests.yaml` の関心領域から選ぶ）
   - 話題のまとまり（同一の話題を判別するため）
5. **スコア計算**: プログラムで計算する（LLM は使わない）。
   - `スコア = 関連度 × 分野の重み + 人気度補正`
   - 人気度は情報源ごとにパーセンタイルに変換してから使う
   - 重みと補正の強さは設定で変更できる
6. **上位選定**: 以下の制約のもとで上位10本を選ぶ。
   - 同じ話題からは1本のみ
   - 1分野につき最大4本（設定で変更可能）。下限は設けない

**出力 `selection.json`**: 選定した記事（順位・スコア・分野・人気度）、全候補のスコアと選定理由、候補の総数。

### 4.2 ② 要約

- **本文取得**: Jina Reader（無料 API キー）で本文を Markdown として取得する。
  - 失敗したら記事ごとに最大3回リトライする（間隔は 2秒 → 4秒 → 8秒）。
  - 3回とも失敗した記事は諦め、選定で11位以下だった候補を繰り上げる。
  - RSS 概要で本文の代わりにすることはしない。
- **記事の要約**: Claude **Opus 5.5** を1記事につき1回、並行して呼び出す。
  - 出力は構造化データとし、`zod` で検証する。
  - 文字数は指定せず、フォーマットとプロンプトに従ってまとめさせる。
  - プロンプトは `prompts/summarize.md` で管理する。

  | 項目 | 内容 |
  |---|---|
  | `title` | 日本語のタイトル |
  | `domain` | 分野 |
  | `what` | 何が起きたか／何の記事か |
  | `why_it_matters` | なぜ重要か |
  | `key_points` | 技術的なポイント（複数可） |
  | `caveats` | 注意点・限界（記事に記載がある場合のみ） |
  | `url` | 元記事の URL |

- **今日のタイトル**: 全記事の要約がそろった後、別の呼び出しでその日のダイジェストを表す見出しを1つ生成する。
- **選定結果の引き継ぎ**: 選定の結果（順位・スコア・分野・候補の総数）を digest.json にそのまま書き写す。②はこれらの値を判断に使わない。

**出力 `digest.json`**: 今日のタイトル、各記事の要約、引き継いだ選定結果。

### 4.3 ③ スライド生成

入力は `digest.json` のみ。Gamma の標準エンドポイント `POST /v1.0/generations` を使う。エージェント型（`/agent/generations`）は使わない。

| パラメータ | 値 |
|---|---|
| `textMode` | `generate` |
| `format` | `presentation` |
| `textOptions.language` | `ja` |
| `textOptions` の amount / tone / audience | 指定しない |
| `cardOptions.dimensions` | `16x9` |
| `themeId` | 固定（初回確認時に選定する） |
| `exportAs` | `pdf` |
| `folderId` | Gamma 上に手動で作成した「Tech Digest」フォルダ |
| `cardSplit` | `auto` |
| `numCards` | 25（目安の長さ。設定で変更可能） |
| `imageOptions.source` | `aiGenerated`（画像モデルは指定しない） |

`additionalInstructions` で以下を指示する。

- 原稿にない事実や数値を付け加えない
- 各記事の元記事リンクを必ず残す
- 表現方法（図解・表・レイアウトなど）は自由に選んでよい

**スライドの内容**

- **表紙**
  - 今日のタイトル
  - 注目3本（スコア上位3本の見出しと一言紹介）
  - 分野ごとの内訳（例: AI/LLM 4・フロントエンド 2・…）
  - 日付と選定の規模（例: 312本の候補から10本を選定）
- **各記事**: タイトル、分野、要点、元記事へのリンク。何枚使うか、どう表現するかは Gamma に任せる。
- **並び順**: 分野ごとにまとめ、同じ分野の中ではスコアの高い順。

**処理の流れ**

1. 生成を依頼する。
2. `GET /v1.0/generations/{id}` で約5秒ごとに状態を確認する（Webhook はない）。
3. 完了したら `exportUrl` から PDF をダウンロードする。`exportUrl` は約1週間有効で、誰でもアクセスできてしまうため、ログや永続化データには残さない。

**出力**: PDF のバイナリ、`gammaUrl`、消費クレジット（`credits.deducted`）。

### 4.4 ④ 配信

1つの工程とし、その中で**保存担当**と**通知担当**を別の部品として実装する。保存担当が返した保存先のリンクを、通知担当が使う。

#### 保存担当（Google Drive）

- **認証**: 個人 Google アカウントの OAuth。
  - スコープは `drive.file`。
  - OAuth アプリは「本番」に切り替える（「テスト中」のままだとリフレッシュトークンが7日で失効するため）。
  - リフレッシュトークンは GitHub Secrets に保存する。
  - サービスアカウントは使わない（保存容量を持たず、個人のマイドライブに保存できないため）。
- **フォルダ構成**

  ```
  TechDigest/
    state.json              ← 掲載済み URL（直近30日分）と前回実行時刻
    YYYY/MM/DD/
      slides.pdf
      digest.md             ← digest.json を人が読みやすい形にしたもの。Gamma URL も記載
      digest.json
      selection.json
  ```

- **保存期間**: 無期限。自動では削除しない。

#### 通知担当（Discord）

Discord の Webhook で以下を投稿する。

- 今日のタイトル
- 10本の記事タイトルと分野
- Drive の PDF へのリンク、Gamma のスライドへのリンク
- 取得できなかった情報源や記事があれば、その一覧

## 5. 設定ファイル

| ファイル | 内容 |
|---|---|
| `config/interests.yaml` | 関心領域（名前、どんな記事が読みたいかの自然文での説明、重み） |
| `config/sources.yaml` | 情報源の一覧と取得パラメータ |
| 選定・生成の設定 | 掲載本数、1分野あたりの上限、スコアの重み・補正、工程ごとの Claude モデル名、`numCards` など |
| `prompts/summarize.md` | 要約のプロンプト |

設定はリポジトリで管理し、変更は編集して push することで反映する。

## 6. 実行・運用

- **実行基盤**: GitHub Actions（非公開リポジトリ）
- **定期実行**: 毎日 7:00 JST（cron は `0 22 * * *` UTC）。混雑時は10〜30分ほど遅れることがある。
  - 前回実行時刻は `state.json` に記録するので、実行されなかった日があっても次の実行で取りこぼさない。
- **手動実行**（`workflow_dispatch`）で選べること:
  - dry-run にするかどうか
  - 対象日
  - どの工程から始めるか
- **同日の再実行**: Drive のファイルを上書きする。掲載済み URL の記録は二重にならないようにする。
- **ローカル実行**: デフォルトで dry-run とする。Gamma・Drive・Discord は呼ばず、結果をローカルのファイルに出力する。

## 7. エラー処理

- 外部 API（各情報源、Jina Reader、Claude、Gamma、Drive、Discord）の呼び出しはすべて、間隔を広げながら最大3回リトライする。

| 状況 | 動作 |
|---|---|
| 一部の情報源の取得に失敗 | その情報源だけスキップして処理を続け、通知に記載する |
| 記事の本文取得に失敗 | 次点の候補を繰り上げ、通知に記載する |
| Gamma が失敗（クレジット切れを含む） | `digest.md` 等を Drive に保存し、テキスト版のダイジェストを Discord に送る |
| Claude または Drive が失敗 | Discord にエラーを通知する |
| ワークフロー自体が失敗 | GitHub Actions の標準のメール通知 |

## 8. 費用

- **Gamma**: Pro プラン（月 4,000 クレジット）の範囲を目安とする。残りクレジットから逆算して生成を止める仕組みは設けない。クレジットが尽きた場合は7章の Gamma 失敗時の動作に従う。
- **Claude**: Anthropic Console で月の利用上限額を設定する。金額は、初回確認で実際の費用を測ったうえで、その2倍程度とする。
- **その他**: GitHub Actions は非公開リポジトリの無料枠内（月2,000分）。Jina Reader は無料 API キー。Google Drive は既存の Google AI Pro の容量（5TB）を使う。

## 10. テスト方針

- Vitest で、ネットワークに依存しない部分を自動テストする。
  - 対象: URL の正規化と重複統合、既出除外、スコア計算と上位選定、JSON スキーマの検証、設定ファイルの検証、digest.md の組み立て
- 外部 API との連携は dry-run と手動実行で確認する。

## 11. 初回確認項目

実装後、最初の生成で以下を確認する。

1. Gamma のテーマを何種類か試し、`themeId` を決める。
2. `textMode: generate` で、原稿にない事実が付け足されていないかを digest.json と照らし合わせて確認する。目立つ場合は `preserve` に切り替える。
3. `numCards: 25` のときに、実際に何枚になり、どう構成されるかを確認する。
4. 日本語と 16:9 で出力されているかを確認する。
5. Gamma の `credits.deducted` と Claude の費用を測り、Anthropic Console の上限額を決める。
